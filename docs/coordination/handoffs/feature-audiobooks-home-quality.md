## 1. Достоверная классификация CEFR

### Причина ошибки

`lib/audio/audiobooks.ts` (было): `estimateAudiobookCefr` проверяла жанровые слова в порядке
`A1 → A2 → C2 → C1 → B1 → B2` и **не искала никаких явных маркеров уровня вообще**. Ключи `märchen`, `grimm`,
`kinder`, `fairy`, `easy` сразу давали `A1` — жанр и имя автора выдавались за уровень владения языком. Каталожный
хук `fetchAudiobooks` усугублял это: при выбранном фильтре `cefrLevel !== "all"` он **принудительно** подставлял
запрошенный уровень как факт (`cefrLevel: estimatedLevel = cefrLevel`), даже когда поиск по IA возвращал
неадаптированный оригинал. Отсюда и «явный B1 иногда становится A1» — по сути, любой уровень мог стать любым
другим просто по выбору фильтра пользователем.

### Что сделано

- `classifyAudiobookCefr` (новая): явный маркер источника (`Niveau A1`, `[B2]`, `Graded Reader A2`, `Der Prozess – B2`)
  → `confidence: "verified"`, всегда приоритет над эвристикой. `Leichtes Deutsch`/`Easy German` без числового кода →
  `approximate A2`. Жанр/автор для B1–C2 → `approximate` (никогда не для A1/A2 — это и есть правило задачи). Нет
  сигнала → `level: null, confidence: "unverified"` вместо старого catch-all `return "B1"`.
- Раздельные списки: авторские фамилии (`mann`, `hesse`, `kant`, …) matched **как отдельное слово**, а не подстрокой —
  иначе `.includes()` ловил «Hoffmann» как совпадение с Thomas Mann, а «Hessen» — с Hermann Hesse (найдено вживую при
  тестировании, см. регрессионный тест). Жанровые существительные (`novelle`, `roman`, `erzählung`) остаются подстрокой
  умышленно — немецкий свободно их компонует («Schachnovelle»).
- `fetchAudiobooks` и `fetchAudiobookDetails` больше не подставляют запрошенный фильтр как факт — классифицируют
  независимо, затем (см. ниже) отфильтровывают несовпадающие.
- **Второй баг, найденный уже вживую при проверке** (был замечен и пользователем в процессе): честная маркировка
  сама по себе не мешала каталогу показывать под фильтром «A1» книги, классифицированные как «≈ B1» — поиск IA
  подобен неточному поиску по жанру, а не настоящему фильтру уровня. Исправлено: при выбранном уровне
  `fetchAudiobooks` запрашивает больший «сырой» пакет (`rows × 6`, максимум 120, один запрос, не N запросов) и
  оставляет только те книги, чей классифицированный уровень **реально совпадает** с запрошенным. Новое поле
  `matchedOnPage` используется в `DiscoverView` вместо необоснованного «148 аудиокниг» (это число IA-поиска, а не
  подтверждённых совпадений).

### Примеры (снято вживую через Internet Archive API, язык de, вкладка «Аудио»)

| Вход (title / author) | До (бы было) | После (`classifyAudiobookCefr`) |
|---|---|---|
| «Märchen» / Gebrueder Grimm | `A1` (по слову grimm) | `≈ B1` (по «erzählung» в описании), confidence=approximate |
| «Der Weg» / — с явным «(Niveau A1)» в названии | тоже мог стать `A1` только случайно | `A1`, confidence=**verified** |
| «Klein Zaches, genannt Zinnober» / E. T. A. Hoffmann | могло стать `≈ B2` (mann-подстрока) | `≈ B2` по «erzählung»/жанру, но **не** по ложному «mann» внутри «Hoffmann» |

## 3. Ускорение загрузки каталога

Архитектура уже была двухфазной **до** этой задачи (UX-редизайн `release/audiobooks-pause`): список загружает только
`identifier,title,creator,description,language,publicdate,downloads,item_size,subject` (без глав), главы грузятся
лениво в `fetchAudiobookDetails` только при открытии карточки; кэш (`audioCacheRef`), `AbortController` на смену
страницы/фильтра и loading/empty/error состояния — присутствовали. N+1 не обнаружено.

Замер (реальный запрос через `archive.org/advancedsearch.php`, live, PAGE_SIZE=18, без фильтра уровня):

- Время ответа: **653 мс**
- Размер тела ответа: **24 136 байт** на 18 карточек
- Запросов на первую страницу: **1** (никаких `archive.org/metadata/...` вызовов до открытия конкретной книги)

Для фильтра по конкретному уровню (после фикса из п.1) размер «сырого» запроса вырос до `rows≤120` за тот же **один**
запрос — компромисс: фильтрация честная, но при обилии approximate-совпадений другого уровня на странице может
оказаться меньше `pageSize` (или ноль) реальных совпадений; это осознанно, см. пустое состояние в п.1.

## 6. Счётчик карточек на сегодня

`computeDeckStats(...).dueCards` и реальный список в `CardsView` уже использовали один и тот же предикат
(`isVariantDue`) — расхождения по алгоритму не было. Расхождение было в **свежести**: `HomeDashboard` считал
`dueCardsCount` через `new Date()` без зависимости от времени и без обновления на смене суток, тогда как
`CardsView` уже тикает `todayEndTime` каждые 60 секунд. `endOfTodayMs` вынесен как общий экспорт из `lib/cards.ts`
(было приватной копией в `CardsView.tsx`) и переиспользован в обоих местах — единая точка отсчёта «сегодня».

Добавлены регрессионные тесты: подсчёт `dueCards` всегда равен независимо построенному списку (new + due-today +
overdue считаются, отдалённая карточка — нет); карточка, просроченная ровно в `23:59:59.999` локального времени,
засчитывается, на секунду позже — нет (граница вычисляется через сам `endOfTodayMs`, без хардкода часового пояса,
поэтому тест корректен в любом TZ); ноль просроченных — репортится как ноль.

## Известные ограничения

- **AI-чат недоступен в этой песочнице**: `/api/ai/chat` отвечает 403 (нет валидного Gemini API-ключа в текущем
  окружении) — ожидаемо и заранее оговорено в задаче. Проверены **имена** переменных окружения в `.env.example`
  (`GEMINI_API_KEY` и т.п.), значения не выводились. AI-обзор в модалке падает на заранее существующий fallback-текст
  (не крашится, деградирует штатно).
- Пагинация под фильтром уровня всё ещё опирается на «сырой» счётчик Internet Archive для номера последней страницы
  (`totalPages`) — точный подсчёт «сколько всего страниц реально дадут совпадение» потребовал бы сканирования всего
  каталога, что противоречит цели «не грузить лишнее». Счётчик **на текущей странице** (`matchedOnPage`) честен;
  общий `totalPages` — приближение для навигации, не обещание, что каждая следующая страница даст совпадения.
- `aibook:audio_progress:*`/`aibook:audio_last_played` в `localStorage` не разделены по пользователю (в отличие от
  паттерна `ns:<userId|guest>:...`, принятого для остального стейта) — это предсуществующее поведение (было так уже
  в `release/audiobooks-pause`), не тронуто в рамках этой задачи, но стоит отдельного тикета для мультипользовательских
