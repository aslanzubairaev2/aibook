# Проверки критических функций

После изменений запускайте `npm test`. Команда автоматически находит все
`*.test.ts` и `*.test.mjs` в `app/`, `components/` и `lib/`: новый тест не нужно
вручную добавлять в `package.json`.

`npm run build` сначала запускает весь набор тестов через `prebuild`. При падении
теста сборка не начинается. Это работает и при выпуске через обычный
`npm run build`; прямой вызов `next build` обходит npm hooks, поэтому не используйте
его как команду выпуска.

В GitHub Actions проверки lint, test и build запускаются независимо для PR в
main/staging и push в main/staging/feature/**/fix/**/chore/**. Ошибка lint не отменяет
тесты. Для запрета merge при красных проверках требуется дополнительно назначить
эти checks обязательными в защите ветки GitHub; эта настройка здесь не изменена.

## Быстрая проверка

`npm run test:critical` проверяет фотоимпорт, обрезку изображений, обработку ответов
Gemini, словарь, создание карточек и основные сценарии обучения. Полный `npm test`
дополнительно покрывает остальные существующие тесты, включая аудио и видео.

Тестовые даты заданы в UTC, поэтому runner устанавливает UTC только дочернему
процессу тестов. Часовой пояс приложения остаётся пользовательским.

## Что защищает фотоимпорт

`lib/db/photoImport.test.ts` вызывает настоящие обработчики Next.js, SDK Gemini,
SDK Supabase, парсеры и хранилища. Вместо внешних сервисов используются локальные
HTTP-серверы, без настоящих ключей, пользовательских данных и расходов на ИИ.

- Фото → пачка → слова → карточки на текущей и старой схеме базы.
- Отсутствие `content_type`, а также отставший кеш схемы записи PostgREST.
- Повторный импорт без дублей, с сохранением множественного числа и SRS-прогресса.
- Ошибки чтения словаря и создания карточек не показываются как успех.
- Ограничение чтения владельцем, в том числе в запасном запросе и MCP.
- Фразы и выражения не превращаются в слова при отсутствующей миграции.
- Фото текста и домашнего задания работают независимо от таблицы словаря.
- Отсутствие входа/ключа, неверный формат и слишком большой снимок, пустой ответ ИИ.

Это серверные интеграционные тесты с имитацией внешних HTTP API, а не тесты
на реальном PostgreSQL и не проверка качества OCR. Камеру телефона, жесты обрезки,
мобильную вёрстку и качество распознавания реального снимка нужно проверять в
браузере на Preview. Такие проверки в этой задаче не выполнялись.

## Перед выпуском изменений схемы

1. Сопоставить миграции из `supabase/migrations/` со схемой целевой базы.
2. Применить нужные миграции в согласованном окружении. Не использовать production
   данные или секреты в Preview без отдельного согласования.
3. Запустить `npm run check:schema` с переменными целевого окружения:
   `NEXT_PUBLIC_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Команда также понимает
   локальные env-файлы Next.js; сами секреты не выводит.
4. Запустить `npm run build`, затем проверить пользовательский сценарий.

`check:schema` делает только SELECT с `limit(0)`: проверяет наличие колонок в
таблицах словаря, пачек, карточек и уроков. При несовпадении схемы или отсутствии
доступа завершается с ненулевым кодом. Это отдельная проверка; автоматически
миграции не применяются. Она не проверяет SQL-ограничения, RLS или качество данных.

Для обнаруженного 14.09.2026 расхождения относятся следующие существующие миграции:

- `20260817120000_pack_training_prefs.sql` — настройки пачек `training`.
- `20260818120000_pack_description.sql` — описание и инструкция пачки.
- `20260914000000_learning_item_types.sql` — типы словаря, карточек и legacy vocabulary.

Последняя миграция также нормализует неподдерживаемые типы в `word`: перед её
применением нужно проверить текущие значения и ограничения в целевой базе.
Исправление кода позволяет сохранять обычные слова без `content_type`, но полная
поддержка фраз и выражений всё равно требует миграции.
